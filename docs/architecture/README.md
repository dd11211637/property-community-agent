# MVP 项目架构

本仓库由四位成员共同维护，目录按系统职责和交付物组织，不按成员或单个业务功能切割。
MVP 采用“前后端分离 + 单一 Python 后端 + PostgreSQL + Agent 编排”的结构，不提前拆微服务。

## 仓库结构

```text
property-community-agent/
├── frontend/                    响应式 Web 前端
├── src/property_agent/          统一 Python 后端与 Agent 运行时
│   ├── platform/                身份、权限、房屋、确认、幂等和审计
│   ├── repair/                  报修业务模块
│   ├── announcement/            公告业务模块
│   ├── billing/                 费用业务模块
│   ├── inspection/              巡检与安防业务模块
│   ├── agent/                   智能体编排
│   └── integrations/            外部系统适配
├── alembic/                     PostgreSQL 正式迁移
├── tests/                       自动化测试
├── testing/                     压测和本地验证支持脚本
├── infra/                       本地及演示环境部署配置
├── scripts/                     初始化、迁移、种子和运维脚本
├── docs/
│   ├── architecture/            架构和边界
│   ├── api/                     API 契约
│   └── decisions/               重要技术决策记录
├── .env.example                 环境变量模板
├── pyproject.toml               Python 项目与质量工具配置
└── README.md                    项目入口和运行说明
```

## 运行架构

```text
浏览器
  │
  ├── 结构化业务页面
  └── 智能体对话入口
          │
          ▼
      FastAPI 后端
  ┌───────────────────────────────┐
  │ 身份与权限 │ 业务服务 │ Agent 编排 │
  │ 状态机     │ 审计幂等 │ 外部适配器 │
  └───────────────────────────────┘
          │                 │
          ▼                 ▼
      PostgreSQL       物业/账单/消息/模型 API
```

后端是业务状态的唯一事实来源。前端和 Agent 都不能直接修改状态；所有写操作必须经过身份、
数据范围、状态机、确认、幂等和审计校验。

Agent 的外部模型只输出严格的意图、置信度、候选槽位或受控只读规划，不持有 Repository 或数据库写权限。
模型建议不能覆盖身份、小区、房屋、确认令牌、幂等键或版本等可信字段；写操作仍调用公开应用服务。
DeepSeek 超时、限流、5xx 或结构错误最多重试一次，然后进入关键词降级。
受控只读规划最多执行五步，只能选择代码白名单中的真实 Application Service 查询工具；
每步记录脱敏参数哈希和结果摘要，不记录完整参数或模型思维链。社区知识查询目前仅使用住户
可见的已发布公告作为正式来源，独立知识库不在第二阶段范围内。

业务事务将通知写入 PostgreSQL Message Outbox，后台发送器独立推进投递状态；业务成功不等同于
外部投递成功。达到重试上限的消息进入失败状态并生成客服人工接管单。当前产品范围只装配站内消息，
不声称已接入真实短信或语音渠道。

登录失败状态同样持久化在 PostgreSQL，避免多进程或重启绕过锁定。边缘 Nginx 执行来源 IP 限流，
应用层按规范化用户名和可信代理转发的来源 IP 维护失败窗口；生产环境必须显式配置可信代理网段。
HTTP 访问日志输出结构化 JSON，只记录请求 ID、方法、路由模板、状态码和耗时，不记录请求体或令牌。

## 后端模块边界

后端采用按业务能力划分的模块化单体，而不是把全部业务代码堆在一个 service 目录：

| 类型 | 模块 | 职责 |
|---|---|---|
| 公共平台 | `platform` | 身份、RBAC、小区/房屋范围、确认、幂等、审计和消息任务 |
| 业务模块 | `repair` | 报修创建、分派、处理、验收、返工和评价 |
| 业务模块 | `announcement` | 公告草稿、受众、审核、发布和撤回 |
| 业务模块 | `billing` | 账单只读查询、规则解释和财务咨询 |
| 业务模块 | `inspection` | 巡检计划、记录、异常和安防事件闭环 |
| 系统编排 | `agent` | 意图路由、信息补全、确认卡片、工具调用和人工接管 |
| 外部适配 | `integrations` | 物业、账单、消息、对象存储和模型服务适配 |

每个业务模块拥有自己的领域规则、应用服务、API/工具适配和持久化实现，但共享统一数据库、
认证入口、事务规范和部署单元。业务模块之间不能直接修改对方的数据，应通过公开应用服务、
事件或稳定 Port 协作。

费用模块的应用服务只依赖 `BillingUnitOfWorkPort`，不导入 FastAPI、SQLAlchemy、ORM 或具体
Repository。生产环境由 `infrastructure/unit_of_work.py` 将账单来源、规则、咨询、幂等和审计
绑定到同一个请求 Session，确保业务记录与审计/幂等原子提交。咨询状态变更必须携带
`expected_version`；账单详情同时按社区和当前房屋过滤。

Agent 写操作只接受确认卡片的 `action_hash`，HTTP 客户端不能提交确认令牌。服务端在恢复会话、
房屋绑定、有效期和参数指纹校验通过后签发令牌；原生支持平台确认的业务命令在业务事务中消费，
其他低风险 Agent 写命令在 Agent 边界完成一次性消费并继续由幂等键保护。该兼容路径应随着各业务
命令逐步原生接入确认 Port 而移除。

开始实现某个业务模块时，沿用现有 `repair` 的内部结构：

```text
<module>/
├── domain/                      实体、状态机、业务错误
├── application/                 用例、命令、查询和 Port
├── adapters/                    HTTP API、Agent 工具和展示转换
└── infrastructure/              SQLAlchemy、Repository 和外部实现
```

未开始开发的模块暂时只保留职责说明，不提前生成空类、假接口或 mock。

## MVP 能力范围

- 公共平台：演示登录、角色权限、小区与房屋绑定、确认凭证、幂等、审计。
- 报修：创建、分派、处理、验收、返工和评价。
- 公告：草稿、受众、审核、发布和撤回。
- 费用：账单只读查询、规则解释和财务咨询。
- 巡检：计划、任务、记录、异常和安防事件闭环。
- 智能体：意图识别、字段补全、工具调用、确认卡片、失败降级和人工接管。
- 前端：住户端、物业工作台和统一对话入口。

## 共同维护原则

- 不按四个人创建四套独立架构，使用 Issue、分支和 Pull Request 划分任务。
- 模块按业务边界划分，不按成员划分；任何成员都可以通过评审修改任一模块。
- 一个功能应同时包含必要的后端、前端、迁移、测试和文档变更。
- 生产代码不引用 `tests/`、`testing/` 或本地模拟数据。
- API 契约和数据库迁移进入代码评审，避免成员之间口头同步造成不兼容。
- 先保证非 AI 业务闭环，再接入 Agent；Agent 不重复实现后端业务规则。
