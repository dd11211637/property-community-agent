# MVP 项目架构

本仓库由四位成员共同维护，目录按系统职责和交付物组织，不按成员或单个业务功能切割。
MVP 采用“前后端分离 + 单一 Python 后端 + PostgreSQL + Agent 编排”的结构，不提前拆微服务。

## 仓库结构

```text
property-community-agent/
├── frontend/                    响应式 Web 前端
├── src/property_agent/          统一 Python 后端与 Agent 运行时
│   ├── platform/                身份、权限、房屋、确认、幂等和审计
│   ├── repair/                  报修业务模块
│   ├── announcement/            公告业务模块
│   ├── billing/                 费用业务模块
│   ├── inspection/              巡检与安防业务模块
│   ├── agent/                   智能体编排
│   └── integrations/            外部系统适配
├── alembic/                     PostgreSQL 正式迁移
├── tests/                       自动化测试
├── testing/                     压测和本地验证支持脚本
├── infra/                       本地及演示环境部署配置
├── scripts/                     初始化、迁移、种子和运维脚本
├── docs/
│   ├── architecture/            架构和边界
│   ├── api/                     API 契约
│   └── decisions/               重要技术决策记录
├── .env.example                 环境变量模板
├── pyproject.toml               Python 项目与质量工具配置
└── README.md                    项目入口和运行说明
```

## 运行架构

```text
浏览器
  │
  ├── 结构化业务页面
  └── 智能体对话入口
          │
          ▼
      FastAPI 后端
  ┌───────────────────────────────┐
  │ 身份与权限 │ 业务服务 │ Agent 编排 │
  │ 状态机     │ 审计幂等 │ 外部适配器 │
  └───────────────────────────────┘
          │                 │
          ▼                 ▼
      PostgreSQL       物业/账单/消息/模型 API
```

后端是业务状态的唯一事实来源。前端和 Agent 都不能直接修改状态；所有写操作必须经过身份、
数据范围、状态机、确认、幂等和审计校验。

## 后端模块边界

后端采用按业务能力划分的模块化单体，而不是把全部业务代码堆在一个 service 目录：

| 类型 | 模块 | 职责 |
|---|---|---|
| 公共平台 | `platform` | 身份、RBAC、小区/房屋范围、确认、幂等、审计和消息任务 |
| 业务模块 | `repair` | 报修创建、分派、处理、验收、返工和评价 |
| 业务模块 | `announcement` | 公告草稿、受众、审核、发布和撤回 |
| 业务模块 | `billing` | 账单只读查询、规则解释和财务咨询 |
| 业务模块 | `inspection` | 巡检计划、记录、异常和安防事件闭环 |
| 系统编排 | `agent` | 意图路由、信息补全、确认卡片、工具调用和人工接管 |
| 外部适配 | `integrations` | 物业、账单、消息、对象存储和模型服务适配 |

每个业务模块拥有自己的领域规则、应用服务、API/工具适配和持久化实现，但共享统一数据库、
认证入口、事务规范和部署单元。业务模块之间不能直接修改对方的数据，应通过公开应用服务、
事件或稳定 Port 协作。

开始实现某个业务模块时，沿用现有 `repair` 的内部结构：

```text
<module>/
├── domain/                      实体、状态机、业务错误
├── application/                 用例、命令、查询和 Port
├── adapters/                    HTTP API、Agent 工具和展示转换
└── infrastructure/              SQLAlchemy、Repository 和外部实现
```

未开始开发的模块暂时只保留职责说明，不提前生成空类、假接口或 mock。

## MVP 能力范围

- 公共平台：演示登录、角色权限、小区与房屋绑定、确认凭证、幂等、审计。
- 报修：创建、分派、处理、验收、返工和评价。
- 公告：草稿、受众、审核、发布和撤回。
- 费用：账单只读查询、规则解释和财务咨询。
- 巡检：计划、任务、记录、异常和安防事件闭环。
- 智能体：意图识别、字段补全、工具调用、确认卡片、失败降级和人工接管。
- 前端：住户端、物业工作台和统一对话入口。

## 共同维护原则

- 不按四个人创建四套独立架构，使用 Issue、分支和 Pull Request 划分任务。
- 模块按业务边界划分，不按成员划分；任何成员都可以通过评审修改任一模块。
- 一个功能应同时包含必要的后端、前端、迁移、测试和文档变更。
- 生产代码不引用 `tests/`、`testing/` 或本地模拟数据。
- API 契约和数据库迁移进入代码评审，避免成员之间口头同步造成不兼容。
- 先保证非 AI 业务闭环，再接入 Agent；Agent 不重复实现后端业务规则。
