# 全功能人工 E2E 验收清单

- 前端入口：<http://localhost:5173>
- 健康检查：<http://localhost:5173/ready>
- 所有演示账号密码：`123456`
- 建议为本轮数据使用唯一标记，例如 `E2E-0813-1730`，避免与历史记录混淆。

| 账号 | 角色 | 主要验证范围 |
| --- | --- | --- |

## 2. 登录、房屋和权限

### 单房屋住户

1. 使用 `zhangsan` 登录。
2. 应直接进入“今天想处理什么？”首页。
3. 顶部应自动显示当前房屋。

### 多房屋住户

1. 使用 `lisi` 登录。
2. 顶部“当前房屋”应提供多个选项。
3. 切换房屋后进入“账单费用”，页面应正常刷新且只展示所选房屋数据。

### 越权和隔离

1. `zhangsan` 打开“管理工作台”，应看到权限拒绝提示。
2. `wangwu` 登录后尝试房屋业务，应被拒绝或要求有效房屋。
3. `qianqi` 不应看到社区 A 住户的工单、账单、公告或消息。
4. `manager` 打开“管理工作台”，应看到待办、失败消息和高风险事件指标。

## 3. Agent 对话入口

使用首页“发送给社区智能体”输入框逐项验证。

### 账单与上下文

1. `zhangsan` 输入“查询这个月的账单”。
2. 应返回当前月份、金额和费用明细，不应混入其他月份。
3. 紧接着输入“那上个月呢”。
4. 应理解为同一账单上下文并切换到上个月。

### 公告和可信信息边界

1. 输入“今天会停水吗”。
2. 应只返回已发布且日期、受众匹配的公告；没有结果时明确说明未查到。
3. 输入“物业电话是多少”。
4. 如果资料库没有号码，应明确未查到，不得编造电话。

### 报修信息补全

1. 输入“我要报修”。
2. 根据提示输入“灯具损坏”。
3. 点击位置选项“客厅”。
4. 应出现“确认提交这条报修吗？”对话框，且只展示住户可理解的中文字段。
5. 先点击“取消”，确认没有新工单。
6. 再输入“客厅电灯坏了，需要报修”。
7. 出现确认框后刷新页面，确认框应恢复。
8. 点击“确认提交”，只能新增一张工单，回复应包含“报修已提交”。

### 工单查询

1. 在“报修服务”复制一张工单的 `WX-...` 业务编号。
2. 回到首页输入“查询工单进度 WX-...” 。
3. 应返回该工单真实状态和时间线，不应把普通文本当作工单号。

### 高风险事件

1. `zhangsan` 输入“1栋厨房闻到强烈燃气味，请上报事件”。
2. 确认框应显示地点、事件描述和高风险信息。
3. 点击“确认提交”。
4. 事件应创建并明确进入人工接管；Agent 不得自行关闭高风险事件。

### 安保查询

1. `security_guard` 输入“巡检任务都完成了吗”。
2. 应只展示本人可见任务和真实完成度，不能误显示为公告卡片。

## 4. 报修完整闭环

使用带唯一标记的描述，例如“`E2E-0813-1730 客厅灯具闪烁`”。

1. `zhangsan` →“报修服务”→“新建报修”，填写位置和描述。
2. 点击“核对并提交”→“确认提交”，状态应为 `PENDING_ASSIGNMENT`。
3. `manager` 打开该工单→“派单”，选择“维修工老张”，状态应进入待接单。
4. `repair_worker` 打开该工单→“接单”→确认。
5. 点击“提交完工”，填写完工说明，状态应为 `PENDING_VERIFICATION`。
6. `zhangsan` 打开工单→“要求返工”，填写返工原因，状态应为 `REWORKING`。
7. `repair_worker` 点击“提交返工完工”，填写说明。
8. `zhangsan` 点击“验收通过”→确认，再点击“评价”并填写评价。
9. 最终状态应关闭，详情时间线应包含创建、派单、接单、完工、返工、返工完工、验收和评价。

额外检查：`manager` 的派单框只显示工作人员姓名，不要求手填 UUID。

## 5. 公告完整闭环

### 批准、发布和撤回

1. `customer_service` →“社区公告”→“新建草稿”。
2. 标题使用唯一标记，填写正文；楼栋留空代表全社区。
3. 保存草稿→“送审”→确认，状态应为 `PENDING_REVIEW`。
4. `manager` 打开公告→“批准”→确认。
5. 点击“确认发布”，必须再次点击“二次确认并发布”。
6. 状态应为 `PUBLISHED`，`zhangsan` 应能看到该公告。
7. `manager` 点击“撤回”，填写原因，状态应为 `WITHDRAWN`。
8. 住户刷新后不应再把撤回公告当作已发布公告展示。

### 驳回

1. `customer_service` 再创建一条新草稿并送审。
2. `manager` 打开公告→“驳回”，填写明确原因。
3. 状态应为 `REJECTED`。
4. `customer_service` 应看到驳回状态和原因。

## 6. 账单与财务咨询

1. `zhangsan` →“账单费用”，确认只展示当前房屋账单。
2. 打开账单详情，检查金额、费用类型、账期、规则版本、数据时间和版本。
3. 点击“发起财务咨询”，填写唯一主题和问题描述。
4. 确认后咨询先保存为 `DRAFT`。
5. 刷新页面，草稿仍应存在。
6. 打开咨询→“提交咨询”，状态应为 `SUBMITTED`。
7. 页面不得提供支付、退款、改账或减免操作。

说明：财务答复和申诉后端契约已有测试，但当前 Web 没有财务人员答复工作台；这部分不能作为人工浏览器闭环声称已完成。

## 7. 巡检任务闭环

1. `manager` →“巡检与事件”→“新建巡检任务”。
2. 填写唯一标题、任务说明和路线点位 `1栋大厅,地下车库`。
3. 创建后点击“分派”，选择“安保老李”。
4. `security_guard` 打开任务→“开始巡检”→确认。
5. 点击“提交记录”，填写点位和记录内容。
6. `manager` 打开任务→“复核完成”→确认。
7. 最终状态应为 `COMPLETED`，时间线应保留分派、开始、记录和复核。

## 8. 普通安防事件闭环

1. `zhangsan` →“巡检与事件”→“人工上报事件”。
2. 位置使用唯一标记，描述填写“消防通道存在杂物，需要现场处置”。
3. `manager` 打开事件→“分派处置”，选择“安保老李”。
4. `security_guard` →“提交处置”，填写第一次处置记录。
5. `manager` →“退回处置”，填写退回原因。
6. `security_guard` 再次提交完整处置记录。
7. `manager` →“复核通过”→“确认复核通过”。
8. 最终状态应为 `CLOSED`，退回原因和两次处置记录应保留。

## 9. 高风险安防事件闭环

1. `manager` 人工上报事件：类型选择 `GAS_LEAK`，风险选择 `HIGH_RISK`。
2. 填写唯一位置和“疑似燃气泄漏，已隔离现场并通知值班人员”。
3. 分派给“安保老李”。
4. `security_guard` 提交处置记录。
5. 回到 `manager`，此时不应直接出现可执行的“复核通过”。
6. 先点击“确认高风险评级”并二次确认。
7. 再执行“复核通过”。
8. 最终状态应为 `CLOSED`，审计时间线应保留评级确认人。

## 10. 消息和管理工作台

1. `zhangsan` →“消息中心”。
2. 筛选“未读”，选择一条消息点击“标为已读”。
3. 切回全部，点击“全部标为已读”，再筛选未读应为空。
4. 在已读操作后快速切换筛选，列表不得被旧请求结果覆盖。
5. `manager` →“管理工作台”，检查待处理事项、失败消息、高风险事件和接口健康状态。
6. “失败消息与人工接管”区域应展示失败状态、重试次数/上限和人工接管信息。
